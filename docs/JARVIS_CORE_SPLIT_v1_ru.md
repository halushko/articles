# JARVIS — первый этап разделения ядра (не переключён на боевой диалог)

## Почему не просто переместить 600 строк из gateway/api.py

Ветка llm-index уже имеет самостоятельные процессы gateway, research и llm.
Однако gateway/api.py продолжает интерпретировать намерения через
специализированные проверки текста. Перенос этих if в другой контейнер
ничего не решит.

Первый безопасный шаг — выделить **JARVIS Core (планирование)** с
универсальным контрактом для составных запросов и строго отделить
предложение плана от его исполнения.

## Фактическое состояние этого этапа

- Новый контейнер **core** предоставляет POST /v1/plan (внутренняя сеть Docker).
- Gateway предоставляет аутентифицированный POST /api/plan для диагностики.
- Core получает actor-scoped контекст из Research по **новому read-only API**
  /research/planner/context. Сбор контекста не создаёт ни knowledge changes,
  ни pending approvals.
- Core получает список *реально объявленных* возможностей из Research.
  Текущий небольшой allowlist существует для верификации контрактов
  (knowledge.lookup, knowledge.propose, web.search, dialogue.respond).
  Он **не** содержит словарей фраз или названий устройств.
- LLM через POST /plan предлагает последовательность шагов в JSON,
  включая зависимости и уточнения. Core независимо проверяет имена
  инструментов, порядок зависимостей, формат и исходные policy flags.
- Если Qwen предложила несуществующий инструмент, шаг не исполняется,
  частичный план отбрасывается. Ни права, ни одобрение не определяются
  выходом LLM.
- План **только диагностический**: нет исполнения, изменения Home Assistant,
  сохранения знаний, создания approvals или обращения к SearXNG.
- Текущий /api/chat сохраняет поведение и трассировки. Режимы
  apprentice, hybrid, research_only, llm_only не изменены.
- Research по-прежнему единственный владелец SQLite, данные не мигрируют.

## Как проверить

После сборки/подтягивания новых образов:

\`\`\`bash
curl -sS -H "X-Jarvis-Token: $JARVIS_TOKEN" \
  -H 'Content-Type: application/json' \
  http://127.0.0.1:8766/api/plan \
  -d '{"text":"Найди характеристики инвертора, запомни и сравни с настройками", "web_mode":"ask"}'
\`\`\`

Ожидается \`status=proposed\`, \`needs_clarification\`, \`unavailable\`
или \`invalid\`, \`executed=false\` и \`execution_allowed=false\`.
Точный план зависит от локальной модели; выполнение не производится.

Команда \`python -m unittest tests.test_core_planner -v\` проверяет
контракт без Ollama. Обязателен прогон на реальной модели и
сопоставление с ручной разметкой до переключения основного диалога.

## Следующая миграция

1. Зафиксировать contract tests для реальных запросов, нескольких
   намерений, уточнений, смены пользователя и ошибочных plans.
2. Создать Agent Runtime с детерминированными исполнителями, idempotency
   и approvals (первым — web.search), не переносить специфические if.
3. Перевести только безопасные read-only сценарии /api/chat на Core,
   постепенно вывести старую маршрутизацию из gateway.
4. Разделить knowledge.propose, approval manager и инструменты по
   ответственности; NATS для событий добавлять когда появятся
   реальные producers/consumers, а не ради числа микросервисов.
5. После реального тестирования включать действия с устройствами
   **только** с отдельной авторизацией людей и подтверждениями.

Не выполняйте docker compose down -v: volume research_data содержит
SQLite, ollama_models содержит модели.
