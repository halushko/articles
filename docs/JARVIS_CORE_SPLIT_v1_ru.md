# JARVIS Core v0.2 — интерпретация отдельно от выполнения

## Цель

Перенести принятие решений из монолитного gateway/api.py в Core, **не
переписывая SQLite и не создавая набор новых if для пользовательских фраз**.

Ветка содержит новый экспериментальный контур. Он работает параллельно со
старыми режимами и пока НЕ управляет Home Assistant, не подтверждает
знания и не наделяет модель полномочиями.

## Граница ответственности

| Компонент | Что делает | Что не делает |
|---|---|---|
| Gateway | HTTP, токен, пользовательский диалог, трассировка, журнал | Не интерпретирует текст в режиме core |
| Core | Контекст → Qwen-интерпретация → структурированный план → проверка → последовательное выполнение | Не выдумывает факты и не исполняет физические действия |
| Research | Единственная авторитетная SQLite-модель мира, события разговора, долговременные web approvals | Не решает, что делать с новым запросом |
| LLM | Локальная Qwen даёт предложения intent/steps/arguments/dependencies в JSON | Не отвечает на фактические вопросы по своим весам |
| Search | Отдельный сервис SearXNG + ограниченное публичное HTTPS-чтение | Не имеет доступа к мировой SQLite |
| Gemini | Анализ только публичных прочитанных страниц, предоставленных Core | Не получает личную память, не делает Google Search и не вызывает устройства |

Search имеет отдельную SQLite для **операционных rate-limit/аудита**, не для
памяти JARVIS. Research хранит прежний volume research_data, новую схему
мира этот этап не вводит.

Старые endpoints Research web и LLM Gemini остаются для совместимости
старых режимов, но Core использует новые самостоятельные исполнители.

## Один цикл работы

\`\`\`text
User
 ↓
Gateway /api/chat (experiment="core")
 ↓
Core /v1/chat
 ├─ Сначала Research: ожидающее согласование? → проверка actor/session/TTL
 └─ Иначе Research: подтверждённые сущности/факты + активная тема
      ↓
    Qwen /plan (ТОЛЬКО намерения/аргументы/зависимости)
      ↓
    Core: валидация списка существующих capabilities
      ↓
    Core: проверка фактической полноты памяти
      ├─ Нет смысла/нет данных → уточнение
      ├─ Есть подтверждённые факты → ответ из SQLite, без генерации
      └─ Нужны внешние данные → query provenance + политика сети
            ├─ off → остановка
            ├─ ask → durable approval, остановка до разрешения
            └─ auto/approved → Search, не более одного поиска
                    ↓
                Публичные HTTPS страницы
                    ├─ нет страницы → выдержки и ссылки, без генерации
                    └─ есть прочитанная страница → Gemini
                            ↓
                   Проверка ссылок и содержательных слов по источникам
                            ├─ прошла → помеченный источниками ответ
                            └─ не прошла → выдержки + ссылки, без выдумок
\`\`\`

План — DAG из максимум пяти шагов. У каждого шага есть id, capability,
arguments, depends_on. Зависимость может указывать только на предыдущий
шаг. Core выполняет последовательно: если операция ждёт разрешения или
недоступна, следующие шаги НЕ исполняются. Два отдельных поиска
одним планом пока блокируются с уточнением, чтобы не было скрытых расходов.

Предложение knowledge.propose пока требует отдельной будущей реализации
review workflow и не записывает модельные факты. Исполнитель Home Assistant
отсутствует. После подтверждённого поиска составные задачи типа
"поищи → запомни → сравни" сейчас завершаются на подготовке материалов:
следующие операции не запускаются автоматически.

## Защита от «котлет с мёдом»

Qwen **не выступает источником рецепта**. Если пользователь просит рецепт
котлет, а Qwen создаёт поисковый запрос со словом «мёд», которого
не было в сообщении/активной теме, Core останавливается и спрашивает
уточнение. Это универсальная проверка происхождения новых слов запроса,
без таблицы блюд.

Даже у Gemini наличие ссылки [1] недостаточно. Core требует, чтобы
содержательные слова ответа присутствовали в реальном тексте публичного
источника или исходном публичном вопросе. Это намеренно строгая
лексическая проверка: допустимые перефразирования тоже иногда будут
отклонены. Тогда пользователь получит выдержки и ссылки, а не
уверенный, но неподтверждённый рецепт. Лексическое совпадение не
гарантирует истинности — качество источников остаётся важным.

Из мира JARVIS наружу не уходят история сессии, профили, заметки,
данные устройств или пользовательские ключи. Сервис Search получает
только короткую прошедшую проверку фразу.

## Как проверить

По умолчанию Web UI остаётся на «JARVIS · память и обучение».
Можно выбрать «JARVIS Core · новый контур (бета)».

HTTP-вариант после развёртывания новых образов:

\`\`\`bash
curl -sS http://127.0.0.1:8766/api/chat \
  -H "Content-Type: application/json" \
  -H "X-Jarvis-Token: $JARVIS_TOKEN" \
  -d '{"experiment":"core","text":"Найди рецепт котлет","web_mode":"ask","session_id":"YOUR_SESSION_UUID"}'
\`\`\`

Должно появиться web_approval. Разрешение через UI или
\`approval_id\` с \`allow_web_search=true\` запускает **точно записанный**
поисковый запрос один раз. Повторное подтверждение не запускает повторную
операцию. Без session_id для ask нужен новый диалог.

Проверки без Ollama: \`python -m unittest tests.test_core_planner
tests.test_core_evidence_runtime -v\`; общая матрица тестов — GitHub CI.
Реальный quality benchmark на Qwen3B, Gemini и SearXNG **ещё нужен**
перед переключением режима по умолчанию.

## Развёртывание и откат

Образы нового сервиса не публикуются из чернового PR. Не развёртывайте
эту ветку командой docker compose pull, пока не появятся её проверенные
образы. После слияния и зелёного CI публикуются стандартные GHCR latest.

В Compose добавлены только новые core, search и gemini; веб-интерфейс
по умолчанию остаётся старым. Переключение обратно на
эксперимент apprentice сохраняет прежний рабочий путь.

**Не запускать docker compose down -v**: том research_data содержит
память, ollama_models — модели. Новая search_data содержит только
технический журнал запросов.
