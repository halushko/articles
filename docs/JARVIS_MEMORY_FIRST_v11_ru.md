# JARVIS v11 — память раньше моделей, локальная Qwen раньше Gemini

## Зачем изменена архитектура

Раньше JARVIS после успешного поиска рецепта снова вызывал Gemini, если
пользователь просил «дай рецепт котлет». Новый ответ мог отличаться от
найденного, а бесплатная квота Gemini расходовалась впустую.

Новый приоритет в apprentice/hybrid:

1. Серверная безопасность, согласования, подтверждённая память SQLite.
2. Локальные публичные результаты предыдущих исследований (research_findings):
   повторить реальный найденный ответ с URL и происхождением.
3. Локальная Qwen с текущим контекстом, если ответа в памяти нет.
4. Gemini только при явном отказе/зацикливании Qwen и только для публичных вопросов.
5. Для явно НОВОГО поиска — режим ask/auto/off, SearXNG, анализ Qwen;
   при неудаче Qwen резервное обобщение Gemini.

Ни одна модель не является источником разрешений на действия с устройствами.
Контрольные режимы research_only и llm_only сохранены.

## Реальная локальная память результатов

Таблица research_findings хранит вопрос, тему, ответ, публичные URL,
даты и происхождение каждого успешного публичного поиска SearXNG.
Модельные ответы без реально выполненного поиска сюда не записываются.
При первом запуске обновлённого сервиса прежние успешные поиски
переносятся из старого журнала, чтобы ранее найденные рецепты тоже
можно было повторять без интернета.

Результаты помечены «прошлое публичное исследование, не подтверждённое
знание». Неоднозначная тема, просьба проверить новое/актуальное или
прямое «поищи в интернете» не обслуживаются слепо из кэша.

Находки именованного профиля доступны между его сессиями; без профиля
хранятся только для текущей сессии. Выбранный профиль пока не является
криптографической аутентификацией. Не передавать личную память Gemini.

## Очистка диалога

Интерфейс: «История диалогов → 🧹 Очистить текущий диалог и трассировки».
После отдельного подтверждения вызывается
POST /api/sessions/{id}/clear с JSON confirm=true.

В одной транзакции удаляются только реплики выбранной сессии,
трассировки, оценки, события, контекст темы, ожидающие согласования
и аудиты сессионных операций. Профили, подтверждённые знания и
публичные исследования с указанным человеком не удаляются.
Анонимные находки очищаемой сессии также удаляются.

Выгрузка Markdown по кнопке теперь включает только последние 10 ходов,
поэтому не разрастается от старых трасс. JSON остаётся полным архивом.
Полный Markdown доступен по API с format=md и без параметра last.
Ранее сохранённые на компьютере файлы не меняются.

## Состояние задачи и продолжение разговора

Помимо подтверждённой памяти и сохранённых публичных исследований, JARVIS
теперь имеет отдельный **планировщик контекста задачи**:
`services/research/task_context.py`. Он восстанавливает активный предмет
из ограниченного числа **реальных реплик пользователя** в текущей сессии,
отдельно для выбранного `actor_id`. Ответы Qwen, Gemini и найденные
страницы не могут подменить формулировку предмета.

Например:
- «поища рецепт борща» → запрос `рецепт борща`. Одна обычная ошибка ASR
  в командном глаголе не переводит поиск в свободную болтовню.
- «мне нужен классический рецепт, поищи в интернете» →
  `классический рецепт борща` (добавлен ранее упомянутый предмет).
- Повтор этой просьбы после нажатия «Разрешить поиск» сохраняет «борща».
- «найди документацию Home Assistant REST API», потом «официальную
  документацию, поищи в интернете» → поиск документации **этого API**.
- Если в текущей сессии нет однозначной темы и пользователь говорит только
  «поищи в интернете», JARVIS уточняет предмет, а не ищет что попало.

Разрешения остаются отдельными от планирования: определение темы не
открывает доступ к сети. В режиме `ask` запрос согласуется по
**уточнённой строке поиска**, а исполнитель после подтверждения
использует именно её, включая вопрос для локальной Qwen.
Полезные краткие запросы «дай рецепт» / «покажи это» также получают
контекст при поиске по уже сохранённым публичным материалам.
Локальная Qwen получает явное `task_focus`, не только историю реплик.

В трассировке `/apprentice/context` видны метаданные
`task_resolution`: использовался ли контекст, распознан ли поиск,
есть ли предмет и сколько реплик рассмотрено. Сам текст личных запросов
в новые поля трассы не копируется.

Это ограниченный локальный механизм восстановления неполных предметных
фраз, **не полноценная семантическая память**. Если лексической связи
между предметами нет, модель может попросить уточнение. Никакого
специального списка блюд или правил «если борщ» в маршрутизаторе нет.

## Ограничения

Пока это осторожный поиск по темам, не полнотекстовый семантический
ранжировщик и не механизм автоматического исправления противоречий.
Qwen может ошибаться. Веб-поиск в режиме ask всё ещё требует согласия
на каждый НОВЫЙ поиск. Долговременные персональные разрешения — отдельная
функция и не возникают лишь из статистики ответов «да».

## Обновление Windows (Docker Compose использует готовые GHCR-образы)

    git switch llm-index
    git pull --ff-only origin llm-index
    docker compose pull llm gateway research
    docker compose up -d --force-recreate llm gateway research

Не используйте docker compose down -v: research_data содержит SQLite.

Проверка:
- первый новый запрос на публичный рецепт с разрешённым поиском выполняет SearXNG;
- повторное «дай рецепт котлет» для той же темы возвращает memory_public_research
  с исходным ответом и URL, без новой генерации Gemini;
- очистка диалога обнуляет старые трассы, но не подтверждённые знания.
