# JARVIS v0.8 — единая модель диалога, памяти и действий

Эта версия — миграция от отдельного «угадывания» реплик к явному конвейеру.
Модель Qwen нужна для разговора и формулировки ответа, но не выдаёт полномочия
на запись подтверждённых знаний или внешние действия. Обновление сохраняет
существующий volume `research_data` и исходные подтверждения в SQLite.

## Последовательность обработки

```text
Микрофон / текст / планшет / часы
    │  сырой текст + выбранный тип реплики + actor_id + session_id
    ▼
1. Utterance interpretation (question / command / statement / unknown)
    │  no question mark required; user can explicitly select type
    ▼
2. Speaker context: stable actor UUID, device as hint, session per turn
    │  "неизвестный" не наследует личность другого человека
    ▼
3. Retrieval: подтвердившаяся SQLite + граф / непризнанный текст чата
    ▼
4. Policy boundary
    ├─ Direct verified answer (without Qwen)
    ├─ Explicit web.search request → approval ID → exact query → SearXNG
    ├─ Device/destructive command → reject: no executor connected
    ├─ Teaching/renaming → pending proposal → teacher review (not execution)
    └─ Free chat → Qwen with provenance from SQLite, never as fact without verification
    ▼
5. Journal: raw input, route, sources, actor_id, audit of approvals
```

**Важное ограничение:** распознавание «вопрос/команда» пока детерминированное
и поэтому может ошибаться на неоднозначной разговорной речи. Интерфейс
показывает результат ДО отправки и позволяет выбрать
«Вопрос», «Команда», «Утверждение». Префиксы «Вопрос:» и
«Команда:» работают без изменения диктовки. Отдельный аудиоанализ
интонации браузером не реализован.

## Модель идентичности

* `actors`: постоянный UUID человека; имя — изменяемое отображение;
  `graph_node_id` может указывать на уже подтверждённую сущность.
* `actor_devices`: идентификатор конкретного браузера/клиента.
* `actor_device_profiles`: одно устройство может предлагать двух и более
  пользователей. Не существует `device_id = user_id`.
* `research_turns.actor_id`: говорящий фиксируется для **каждой реплики**;
  при смене профиля фронтенд очищает краткую историю Qwen, чтобы не переносить
  контекст между людьми.
* `dialogue_roles`: **legacy**-совместимость. Существующий подтверждённый
  источник `Привет Меня зовут Дима а тебя` корректно восстанавливает
  имя из `apprentice_proposals`. Подтверждения и граф сохраняются без
  удаления или дублирования доказательств.

Профиль и связь с устройством — пока **подсказка для общения**, а НЕ
доказательство личности. Не использовать их как допуск к приватной памяти,
платежам, замкам и опасным командам. Надя регистрируется вручную через
«+ Профиль». Для телефона, часов и планшета можно сохранять подсказки
«Это моё устройство». Если у одного устройства несколько владельцев,
профиль нужно выбирать для реплики.

**Не реализовано:** биометрия и проверка присутствия по голосу,
авторизация конкретного человека, диаризация одновременной речи,
защищённые личные пространства с ACL, интеграция управления реальными
устройствами. Это требует отдельного безопасного дизайна и тестов.
Текущий проект не должен обещать эти возможности.

## Подтверждение действий (operation approval)

Пример разговора:

1. «Найди в интернете рецепт голубцов».
2. JARVIS распознаёт разрешённый инструмент `web.search` и создаёт
   запись `pending_operations` на 300 секунд с UUID, типом, точным
   запросом, сессией и говорящим.
3. JARVIS отвечает: «Поиск ещё не запущен. Скажи “Разрешаю поиск”».
4. «Разрешаю» / «Разрешаю поиск» / «Подтверждаю поиск» **в той же
   сессии и от выбранного говорящего**: одноразовое атомарное согласие.
5. Только после этого производится реальный запрос к SearXNG, результат
   идёт в Qwen как внешнее непроверенное свидетельство.
6. «Не разрешаю», устаревшее окно, смена говорящего или новый запрос
   запрещают предыдущий поиск; повторное согласие нельзя воспроизвести.

**«Да» НЕ разрешает поиск**, чтобы не перепутать согласие с беседой.
Разрешение на интернет и подтверждение знания — разные операции.
Кнопка разрешения использует UUID уже созданной операции, а не булевый
флаг в запросе. `operation_audit` хранит решение и происхождение.

«Выключи свет», «Открой дверь», «Удали всю память» распознаются как
потенциально опасные действия, но не исполняются: нет проверенного
исполнителя. Никакая запись в `world_actions` или вывод Qwen не даёт
реальных системных прав. Когда такой исполнитель появится, он должен
иметь собственные методы, авторизацию, подтверждение точных аргументов,
ограничение прав и журнал результатов. Универсального «выполни команду»
нет и быть не должно.

## Данные после обновления

Используются неразрушающие миграции `CREATE TABLE IF NOT EXISTS` и
`ALTER TABLE ... ADD COLUMN`; существующие `world_entities`,
`graph_nodes`, `apprentice_proposals`, `knowledge_changes` и журналы
не удаляются. Не следует удалять Docker volume
`jarvis-llm-index_research_data` и запускать `docker compose down -v`.

Перед обновлением сделайте корректный SQLite Backup API snapshot базы.
Запускайте приложение после скачивания образов нужного коммита;
повторный запуск контейнеров не сбрасывает базу.

## Диагностика

У каждого ответа отображаются: источник маршрута,
`utterance_intent`, выбранный человек, время и модель.
Просмотр конкретной причины находится в сохранённой истории
(`research_turns.provenance`); решения по инструментам в
`operation_audit`; голосовые подтверждения знаний в
`voice_review_audit`. Пустой или неоднозначный intent не должен
порождать опасные вызовы. Экспериментальный режим «Только LLM»
намеренно не использует эту память.

## Контракт качества перед продолжением

Новые возможности не считаются готовыми, пока не проверены:
восстановление Димы по подтверждённой фразе, два человека и один
планшет, отсутствие межпользовательского переноса в prompt,
правильная классификация вопросов без «?», реальный поиск только
после scoped approval, отсутствие повтора разрешения, отсутствие
исполнителей физических операций, сохранение старых журналов и
тестовый прогон внутри контейнеров. Эти сценарии вынесены в
`tests/test_v08.py` и `tests/test_v08_identity.py`.
