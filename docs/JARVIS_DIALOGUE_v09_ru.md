# JARVIS v0.9 — состояние диалога и политика действий

Реализация в ветке `llm-index`. Этот этап **не добавляет произвольное управление устройствами**; для физических действий нет доверенного исполнителя. Он исправляет маршрутизацию контекста и создаёт точку контроля перед подключением настоящих инструментов.

## Архитектура

```text
Speech/text + session_id + actor_id
                │
                ▼
DialogueCoordinator (SQLite)
   ├─ Есть ли ожидающее действие / проверка знания?
   ├─ Что именно предложено в последнем ответе?
   ├─ Тот же ли человек, сессия и срок?
   ├─ Не осталось ли нескольких несовместимых предложений?
   └─ Policy: допустимо ли краткое согласие?
           │
           ├─ однозначное web.search, риск low ──▶ одноразовое разрешение
           ├─ knowledge.review ──▶ проверка конкретного предложения
           ├─ неоднозначно ──▶ уточнение (ничего не выполнено)
           ├─ физическое/неизвестное ──▶ запрет (ничего не выполнено)
           └─ обычный ответ ──▶ SQLite dialogue history ──▶ Qwen
```

Основные файлы:
- `services/research/dialogue.py` — авторитетный контекст, контроль ожиданий, единый маршрутизатор коротких ответов, политика риска;
- `services/research/approvals.py` — атомарное одноразовое погашение разрешения на **конкретный** `web.search`;
- `services/research/review_voice.py` — проверка конкретных изменений в памяти; вызывается только из маршрутизатора при наличии соответствующего контекста;
- `services/research/sessions.py` — постоянный журнал, происхождение решения;
- `services/llm/api.py` — извлечение описательного `dialogue_frame`, без разрешений на инструменты;
- `services/gateway/api.py` — orchestration и фактическое использование разрешённого публичного поиска.

## Что хранится в SQLite

`dialogue_frames` сохраняет текущую тему, цель, последний вопрос ассистента, последний маршрут, намерение, время и ID последнего хода **для пары (session_id, actor_id)**.

`research_turns` хранит неизменённые реплики, результаты, идентификаторы подтверждений и источники. В Qwen подаётся история из сервера, привязанная к выбранному собеседнику; история, присланная браузером, не подменяет сохранённую, когда есть сессия.

`pending_operations` и `voice_review_queue` — единственные источники ожидающих операций/проверок. Они не создаются из слов модели в ответе и не считаются подтверждёнными автоматически.

## Правила согласия

1. `да` **не** является универсальным разрешением.
2. Для публичного поиска в режиме `ask` короткое `да` возможно только после **последнего предложенного поиска**, в той же сессии и от того же профиля, в пределах TTL 5 минут, при отсутствии других ожидающих операций.
3. Для проверки знаний короткое согласие возможно только после соответствующего предложения, со сверкой ID записей в очереди.
4. Если предложения конфликтуют, требуется уточнение; действие не выполняется.
5. После любого другого хода короткое согласие не может оживить прежнее разрешение.
6. `device.control`, `data.delete` и неизвестные виды операций **не имеют доверенного исполнителя**. Даже при понимании намерения JARVIS ничего не выполняет; выученное правило не изменяет эту политику.
7. Отдельное действие через кнопку имеет конкретный `approval_id`, и по-прежнему проверяется по сессии, профилю и TTL.

Контекст пользователя и смысл фразы — **подсказки для маршрута**, но не доказательство личности. Профили устройства не являются аутентификацией. Подключая реальную Home Assistant интеграцию, потребуется отдельная серверная идентификация пользователя, ACL по устройствам, независимая оценка опасности операций и проверка фактического результата изменения состояния. Пока такие гарантии отсутствуют, физические операции заблокированы.

## Границы навыков модели

Qwen (один вызов для неочевидных реплик) возвращает структурированный `dialogue_frame` с полями `topic`, `goal`, `assistant_question`, а также обычные `reply`, `intent`, `learning`, `needs_web`, `proposals`. Это данные для следующего диалога, а не разрешение вызвать инструмент.

Прямые однозначные запросы публичного поиска обрабатываются без Qwen. Поисковый запрос извлекается из содержания просьбы: «найди в интернете рецепт пюре» → «рецепт пюре».

## HTTP и тесты

- `POST /research/dialogue/resolve`: `{session_id, actor_id, text, web_enabled}`; результат `handled`, `status`, `category`; выполнение устройства отсутствует.
- `GET /research/dialogue/context/{session_id}?actor_id=...`: сохранённая цель, контекст, краткая история и ожидающие операции.
- Запись хода `POST /research/sessions/{sid}/turns` автоматически обновляет `dialogue_frames`.

`python -m unittest discover -s tests -v` проверяет реплики без знаков вопроса, одноразовые разрешения, истечение TTL, смену темы и говорящего, конфликт нескольких ожиданий, запрет опасных операций, сохраняемость состояния и API.

## Следующий этап

Здесь намеренно нет мнимых вызовов Home Assistant. Подключение реального устройства потребует отдельного проверенного адаптера и политики на уровне конкретных сущностей, параметров и контекста (например, выключение лампы и отключение питания сервера — разные риски). Нельзя считать внедрённое в SQLite правило разрешением для исполнительного инструмента.
