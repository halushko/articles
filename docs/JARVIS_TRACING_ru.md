# JARVIS — диагностика всех режимов в экспорте диалога

Начиная с этой версии, существующая кнопка **«📥 Скачать диалог + трассировку .md»** скачивает тот же журнал SQLite, но после каждого **нового** хода появляется секция `### 🔬 Трассировка выполнения` с диагностическим JSON. Кнопка «Экспорт JSON» сохраняет ту же структуру под `turn.provenance.debug_trace`. Отдельный лог-файл не нужен.

Обработаны все четыре режима интерфейса:

| UI | `experiment` | Что покажет трасса |
| --- | --- | --- |
| Ученик | `apprentice` | чтение SQLite, actor-scoped dialogue, memory/graph/context, классификация, проверки разрешений, LLM planning и web-поиск |
| Индекс → LLM | `hybrid` | старый индекс `/resolve`, попытка распознать команду, при отсутствии команды — изолированный baseline `/chat` |
| Только индекс | `research_only` | разрешение индексом, отказ от свободного диалога при отсутствии знаний |
| Только LLM | `llm_only` | изолированный контрольный вызов Qwen без SQLite |

**Важно:** трассировка не меняет поведение маршрутизатора и не подключает память/поиск туда, где их не было. Она позволяет увидеть несоответствие между ожиданиями и реальным путём. Например, для режима `hybrid` это может выглядеть как запрос к `/resolve` с `is_command=false`, затем `/chat` с `memory_injected=false` и `conversation_history_injected=0`. Это объясняет, почему модель не знает подтверждённое имя и предыдущую тему: ошибка в контуре передачи контекста, а не обязательно в самой Qwen.

## Структура следа

Каждый `debug_trace` содержит:

- `request_id` — уникальный идентификатор запроса из интерфейса (если клиент передал).
- `selected_mode`, `profile`, `ablation`, `web_mode`, `actor_id`, `session_id` — входные переключатели и выбранный профиль (не доказательство личности).
- `steps[]` — относительное время `elapsed_ms`, этап и результат: `gateway.received`, `gateway.phase`, `gateway.route_selection`, `service.request`, `service.response`, `service.error`, `gateway.outcome`.
- `steps[].details.input` — **не сырой запрос**, а тип запроса к сервису, число сообщений истории, наличие памяти, выбор профиля.
- `steps[].details.output` — данные о найденных знаниях, выбранном маршруте, наличии прямого SQLite-ответа, обработке намерений, состоянии операций, web-источниках, результате планировщика.
- `prompt_trace` в ответах LLM — фактическое число и длина сообщений, их роли, источник истории, наличие памяти и capability registry, длина контекста и fingerprint системного промпта. Это информация о **реально сформированном запросе к Ollama**, а не уверения модели о её памяти.
- `outcome` — итоговый маршрут и время. При HTTP ошибке сохраняется `chat_error` с диагностикой, если SQLite доступна.

Число этапов ограничено 80 для одного хода. Полный raw prompt, user credentials, tokens, поисковые страницы и содержимое внешних ответов не дублируются в диагностике. Однако обычные реплики/ответы и источники всё равно содержатся в скачанном разговоре, поэтому **перед публикацией файла проверяй персональную информацию**.

## Как проверять

После установки новой версии:

1. Выбрать **Индекс → LLM** и спросить «Как меня зовут?». Нажать «Скачать диалог + трассировку .md». Найти последний `selected_mode: hybrid` и события `/resolve`, `/chat`. `prompt_trace.memory_injected=false` будет свидетельствовать об отсутствии SQLite-памяти в текущем LLM-вызове.
2. Выбрать **Ученик**, спросить то же самое и сравнить: `/apprentice/context` покажет `identity_roles` и `persisted_history_turns`; если вызвана модель, `/analyze` покажет фактический источник истории.
3. После разговора о люстре спросить «Откуда информация?» и «Поищи в интернете». По trace видно, попал ли старый предмет разговора в историю Qwen, попытался ли gateway вообще создать поисковую операцию, или отдал обычный `llm_fast`.
4. Для любой ошибки 4xx/5xx с сохранённой сессией посмотреть `chat_error`, этап сбоя, сервис и HTTP status. При полной недоступности SQLite сохранение в .md невозможно; тогда UI выдаёт ошибку журнала.

Старые реплики, записанные до обновления, **не имеют** `debug_trace`. Их нельзя реконструировать задним числом: достаточно воспроизвести проблемный сценарий после деплоя.

Обновление: `git switch llm-index && git pull origin llm-index`, далее `docker compose pull && docker compose up -d`. Не применять `down -v`, чтобы не удалить базу SQLite.
