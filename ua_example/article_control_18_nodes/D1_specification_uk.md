# Специфікація процесу відновлення доступу

- **Ідентифікатор документа:** D1
- **Версія і статус:** 1.0 — контрольна специфікація
- **Власник процесу:** керівник Service Desk
- **Область:** відновлення доступу користувача до корпоративного програмного продукту

Документ визначає наскрізний процес від отримання звернення до закриття
інциденту. Він є основним джерелом топології контрольного графа: 18 процесних
вузлів, 21 перехід, дві діагностичні альтернативи та спільний етап перевірки.

## 1. Межі процесу

- **Вхід:** користувач повідомляє, що не може отримати доступ до продукту.
- **Вихід:** інцидент закрито або зареєстровано ескалацію й повідомлено користувача.
- **Альтернативи діагностики:** відновлення ідентифікації або програмної платформи.
- **Системи:** ITSM, IAM, зовнішній IdP, Monitoring та Orchestrator.

| Вузол | Операція | Тип | Роль | Система |

| v2 | Зареєструвати інцидент | дія | Service Desk | ITSM |
| v3 | Визначити пріоритет інциденту | дія | Service Desk | ITSM |
| v4 | Класифікувати інцидент | дія | Service Desk | ITSM |
| v5 | Визначити тип несправності | умова | Service Desk | ITSM |
| v6 | Перевірити стан облікового запису | дія | Identity Analyst | IAM |
| v7 | Перевірити політику автентифікації | дія | Identity Analyst | IAM |
| v8 | Перевірити доступність зовнішнього IdP | дія | Identity Analyst | External IdP |
| v9 | Відновити доступ користувача | дія | Identity Analyst | IAM |

## 3. Правила маршрутизації

| Перехід | Умова | Обов'язкова дія |
|---|---|---|
| v5 → v6 | Ознаки проблеми з обліковим записом або автентифікацією | Продовжити за регламентом D2 |
| v5 → v10 | Ознаки недоступності сервісу або платформи | Продовжити за регламентом D3 |
| v9 → v14 | Доступ відновлено в IAM або через зовнішній IdP | Незалежно перевірити результат |
| v13 → v14 | Платформу відновлено через Orchestrator | Незалежно перевірити результат |
| v15 → v17 | Відновлення успішне | Повідомити користувача |
| v15 → v16 | Відновлення неуспішне | Зареєструвати ескалацію |
| v16 → v17 | Ескалацію зареєстровано | Повідомити користувача |
| v17 → v18 | Користувача повідомлено | Закрити інцидент |

Гілки ідентифікації та платформи є альтернативними. Один інцидент проходить
одну діагностичну гілку та переходить до спільної перевірки у v14. За
негативного результату після v15 спочатку виконується ескалація v16, після чого
про результат повідомляють користувача у v17 і закривають інцидент у v18.

## 4. Критерії завершення

- Результат підтверджено контрольованим входом або технічною перевіркою.
- У записі ITSM збережено маршрут, докази та ідентифікатор зміни або ескалації.
- Користувача повідомлено.
- Інцидент закрито або передано через зареєстровану ескалацію.
