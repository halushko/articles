# Documentation to Process Hierarchy

Дослідницький прототип для сегментації Markdown-документації, перегляду її
структури та побудови багаторівневої процесної моделі.

## Web MVP у Docker Compose

Web-застосунок дає змогу запустити сегментацію без командного рядка:

- обрати один із вбудованих англомовних наборів документації;
- або завантажити ZIP з UTF-8 Markdown-документами;
- зберегти результати для кожної версії документа в PostgreSQL `JSONB`;
- переглянути карту явних посилань між документами з вихідними цитатами;
- переглянути дерево `документ → розділ → сегмент` без хибного трактування
  порядку абзаців як процесного потоку;
- для вбудованого або завантаженого набору побудувати процесну модель
  `L0 → L1 → L2`, перемикати рівні та розгортати або згортати окремі етапи;
- простежити кожну атомарну дію до одного або кількох сегментів документації;
- завантажити результат як ZIP з окремими JSON-файлами та маніфестом.

### Запуск

```bash
cp .env.example .env
```

Задайте у `.env` локальний пароль PostgreSQL. Ключ LLM-провайдера є
необов'язковим:

```dotenv
POSTGRES_PASSWORD=replace-with-a-local-password
LLM_API_KEY=replace-with-your-api-key
```

Якщо `LLM_API_KEY` порожній або встановлено `LLM_ENABLED=false`, застосунок
показує `Без LLM`, але продовжує будувати процесну модель детермінованими
правилами. LLM є покращенням extraction, а не обов'язковою залежністю.

Ключ використовується лише сервером і не передається браузеру. Файл `.env`
виключений з Git. Типово застосунок звертається до OpenAI-сумісного endpoint
`https://api.openai.com/v1/chat/completions` і використовує модель, зазначену в
`LLM_MODEL`. Після налаштування виконайте:

```bash
docker compose up --build
```

UI буде доступний за адресою <http://localhost:8080>. Під час старту застосунок
автоматично виконує Alembic-міграції. Дані PostgreSQL зберігаються в named
volume `postgres-data`. PostgreSQL доступний локальним інструментам на
`127.0.0.1:5432` (порт можна змінити через `POSTGRES_PORT`).

Зупинити сервіси:

```bash
docker compose down
```

Видалити також локальні дані PostgreSQL:

```bash
docker compose down --volumes
```

### API

Створення запуску на вбудованих документах:

```bash
curl -X POST http://localhost:8080/api/v1/runs \
  -F source=example \
  -F example_id=home-internet-connection
```

Доступні `example_id` показуються в UI і визначаються файлами `example.json`
у підкаталогах `EXAMPLE_CATALOG_DIR`. Алгоритм не містить окремої логіки для
конкретного прикладу.

Завантаження власної документації:

```bash
curl -X POST http://localhost:8080/api/v1/runs \
  -F source=upload \
  -F archive=@documentation.zip
```

Додаткові endpoints:

```text
GET /api/v1/runs/{run_id}
GET /api/v1/runs/{run_id}/result
POST /api/v1/runs/{run_id}/documentation-graph
GET /api/v1/runs/{run_id}/documentation-graph
POST /api/v1/runs/{run_id}/process-model
GET /api/v1/runs/{run_id}/process-model
GET /health/live
GET /health/ready
GET /docs
```

Після завершення сегментації процесна модель будується окремим запитом:

```bash
curl -X POST http://localhost:8080/api/v1/runs/{run_id}/process-model
```

Відповідь містить `process_model.hierarchy`, provenance для вузлів і переходів
та warnings. Якщо LLM налаштована, перший виклик може тривати до кількох хвилин;
без LLM використовується локальний deterministic extractor. Наступний
ідентичний виклик повертає кеш.

### Версіонування і кеш

SHA-256 обчислюється з початкових байтів кожного документа. Але ключ кешу
сегментації містить три компоненти:

```text
document_sha256 + segmenter_version + config_sha256
```

Тому зміна алгоритму або його конфігурації створить новий результат навіть для
того самого документа. Хеш усього корпусу обчислюється з відсортованого списку
`path + document_sha256`, а не з байтів ZIP: службові timestamps або порядок
файлів в архіві не змінюють ідентичність набору.

LLM-виділення кешується окремо за ключем:

```text
corpus_sha256 + analyzer_version + llm_config_sha256
```

Тому повторний запуск того самого корпусу з тією самою моделлю, схемою і
prompt-версією не витрачає токени повторно. Зміна моделі або параметрів створює
новий результат, не перезаписуючи попередній.

Оригінальні завантажені документи не зберігаються. PostgreSQL містить їхні
хеші, метадані запуску і JSON-картки. ZIP результату формується з БД на запит.

### Структура результату

```text
result.zip
├── manifest.json
├── documentation_graph.json  # після побудови графа
├── process_model_hierarchy.json  # після побудови процесної моделі
├── process_model_l0.json
├── process_model_l1.json  # якщо рівень сформовано
├── process_model_l2.json  # якщо рівень сформовано
├── aggregation_results.json
├── provenance.json
├── process_model_warnings.json
├── documents/
│   ├── 001_document.<hash>.fragments.json
│   └── ...
├── all_fragments.json
└── errors.json
```

Поточні обмеження upload-пайплайна: лише `.md`, UTF-8, до 100 документів,
20 MB для ZIP і 50 MB після розпакування. Перевіряються небезпечні шляхи,
символічні посилання, шифровані записи, дублікати та unsupported-формати.
Детерміновані мовні сигнали наразі орієнтовані на англомовну документацію;
адаптер входу та extraction-ядро розділені, тому інші формати й мови можна
додавати без зміни моделі графа.

## Перегляд документації

Після сегментації вкладка **Documentation** створює окремий
версіонований результат у таблиці `documentation_graph_results`. UI не малює
всі структурні ребра на одному полотні. Натомість він має два читабельні види:

- **Corpus map** — картки документів і лише явні посилання між ними. Кожне
  посилання можна розгорнути та побачити точну цитату, яка його підтверджує;
- **Document structure** — дерево розділів і сегментів одного вибраного
  документа у вихідному порядку.

Поточний builder додає лише твердження, які можна відтворити без LLM:

- `contains` — структурна належність документа, розділу або сегмента;
- `document_order` — порядок сегментів у вихідному файлі;
- `references` — явне згадування повної назви іншого документа.

`document_order` навмисно не називається `process_flow`: розташування двох
фрагментів поруч ще не доводить причинно-часову залежність між бізнес-діями.
JSON графа містить статус `semantic_analysis: not_started`: цей шар описує
документацію, а не бізнес-процес.

## Ієрархічна процесна модель

Вкладка **Process model** доступна для вбудованого набору та для довільного
коректного ZIP незалежно від наявності LLM. Результат зберігається в
`process_model_results`. Кількість вузлів і переходів визначається фактичним
змістом документації, а не фіксованою схемою D1–D5.

Побудова має два режими extraction та детермінований етап формування ієрархії:

1. У `auto`-режимі налаштована LLM отримує активні leaf-сегменти всього корпусу
   та повертає структурований граф `L0`. Без ключа або при помилці провайдера
   локальний extractor виділяє лише явно підтверджені дії, умови й переходи.
2. Спільний детермінований алгоритм спочатку відновлює каркас керування
   процесом — послідовності, шлюзи, альтернативні гілки, точки злиття та
   завершення. Після цього він формує кандидатів `L1` за межами іменованих
   розділів документації, а `L2` — за неперервними областями процесу навколо
   знайдених split/join-регіонів. Явні неперетинні межі підпроцесів зберігаються
   на `L1` як структурні кандидати; `Q` для них також обчислюється й показується,
   але не скасовує безпосередньо задокументовану межу. Кандидати `L2` проходять
   поріг `Q`, перевірку цілісності розгалуження та детермінований відбір без
   перекриття.

Локальний extractor не прив'язаний до назв D1–D5 або до предметної області й
працює поверх нормалізованих карток. Наразі вхідним адаптером є Markdown. Він:

- відокремлює процедурні документи (`guide`, `procedure`, `runbook`, `standard`
  тощо) від політик, довідників і словників; за відсутності явного типу
  використовується наявність кількох розділів із діями;
- створює атомарні дії тільки з action-bearing фрагментів і не перетворює
  заборони або описові правила на кроки процесу;
- зберігає порядок дій усередині іменованого процедурного розділу та порядок
  самих розділів як явно позначену гіпотезу;
- розбирає `IF–THEN` до звичайного поділу за маркером `then`, а
  `IF–THEN–ELSE` — до двох альтернатив одного шлюзу. В іменованому розділі
  рішення одна явна гілка отримує шлях `Otherwise` до наступного розділу;
  умовне речення поза таким розділом залишається підписаною умовною дією, щоб
  не вигадувати відсутню в джерелі альтернативу;
- розпізнає явно названі результати рішення (наприклад, `recovered` і
  `unresolved`) та зв'язує кожний результат із відповідним наступним розділом;
- сприймає точне посилання на назву іншого процедурного документа як виклик
  підпроцесу; кілька таких посилань створюють split, а повернення до наступного
  розділу документа-виклику — join;
- не додає довільне ребро лише через сусідство двох документів у ZIP.

Гіпотези послідовності мають нижчу довіру: `confidence = 0.55` для окремих дій
одного процедурного розділу, `0.74` між послідовними іменованими розділами та
`0.35` для action-bearing речень одного абзацу. Вони позначаються як
`Low-confidence hypothesis` і потрапляють до warnings. Явна нумерація, умова
або точне міждокументне посилання мають вищу confidence та власне джерельне
пояснення.

Кожний прийнятий вузол і перехід `L0` має посилатися на один або кілька
фрагментів, які справді були передані моделі. Сервер відхиляє невідомі fragment
refs, невідомі вузли, self-loop, conditional edge без умови, дублікати ключів і
confidence поза діапазоном `0..1`. Це забезпечує простежуваність результату,
але не є формальним доказом істинності інтерпретації LLM: користувач усе одно
має перевіряти цитату, причину зв'язку та confidence у правій панелі.

На полотні показуються лише процесні переходи зі стрілками; умови альтернатив
підписані біля відповідних ребер. Довгі альтернативні переходи прокладаються
окремою нижньою трасою, тому вони не ховаються під проміжними картками.
Подвійний клік або кнопка `+` розгортає один етап до дочірніх елементів, а `↑`
згортає їх назад. Можливий також прямий
перехід до повного `L0`, `L1` або `L2`. Після вибору вузла UI показує роль,
систему, атомарні складники, оцінку `Q` та цитати з вихідних документів.

Агрегування реалізує описаний у статті контрольний метод:

```text
Q(C) = 0.2 × S_txt(C) + 0.4 × S_ctx(C) + 0.4 × S_flow(C)
```

- `S_txt` — середня косинусна подібність назв дій у TF-IDF-представленні
  символьних 3–5-грам;
- `S_ctx` — середнє часток домінуючих ролі та інформаційної системи; значення
  `Unknown`, `N/A` та `unspecified` не вважаються спільним контекстом і не можуть
  штучно створити `S_ctx = 1`;
- `S_flow` — співвідношення внутрішніх і граничних переходів;
- пороги: `0.65` для `L0 → L1` і `0.50` для `L1 → L2`;
- для структурного `L1`, межі якого прямо задані розділами, викликами
  підпроцесів і split/join-регіоном, `Q` є діагностичною оцінкою, а не підставою
  зруйнувати задокументоване розбиття;
- кандидати сортуються детерміновано, не можуть перекриватися та окремо
  перевіряються на цілісність розгалуження.

### Конфігурація та чесні обмеження

```dotenv
PROCESS_MODEL_MODE=auto
EXAMPLE_CATALOG_DIR=examples
LLM_ENABLED=true
LLM_BASE_URL=https://api.openai.com/v1
LLM_MODEL=gpt-5-mini
LLM_RESPONSE_FORMAT=json_schema
LLM_TIMEOUT_SECONDS=180
LLM_MAX_INPUT_CHARS=120000
LLM_MAX_OUTPUT_TOKENS=12000
LLM_REASONING_EFFORT=low
```

Доступні режими `PROCESS_MODEL_MODE`:

- `auto` — LLM із автоматичним deterministic fallback; рекомендований режим;
- `deterministic` — завжди локально, без зовнішніх LLM-запитів;
- `llm` — надавати перевагу LLM, але з локальним fallback.

`LLM_ENABLED=false` явно вимикає LLM-виклики. За відсутності `LLM_API_KEY`
застосунок переходить у той самий режим і показує `Без LLM`, але процесна модель
залишається доступною. Якщо провайдер підтвердив вичерпання квоти або кредитного
балансу, LLM вимикається до перезапуску процесу, а поточний запит автоматично
завершується локальним extractor-ом. Тимчасова помилка провайдера також дає
fallback для поточного запуску, але не вимикає наступні LLM-спроби.

`json_schema` є рекомендованим режимом: провайдер має підтримувати OpenAI-style
Structured Outputs. Для сумісного сервера без цього режиму можна встановити
`LLM_RESPONSE_FORMAT=json_object`; серверна валідація результату все одно
залишається обов'язковою.

`LLM_REASONING_EFFORT=low` залишає основну частину completion-бюджету для
великого структурованого JSON. Якщо провайдер не підтримує цей OpenAI-параметр,
задайте порожнє значення `LLM_REASONING_EFFORT=`.

LLM-гілка робить один запит на корпус, щоб модель бачила міждокументні
залежності. Якщо serialized prompt перевищує `LLM_MAX_INPUT_CHARS`, операція
завершується явною помилкою замість непомітного обрізання тексту. Для великих
корпусів наступним інженерним кроком має бути двофазний extraction/linking з
порційною обробкою та reconciliation, а не просте збільшення ліміту.

LLM не отримує інструментів і не виконує команди з документації; фрагменти
позначені як недовірені дані. Проте перед використанням зовнішнього провайдера
потрібно врахувати політику конфіденційності документації та самого провайдера.

Без LLM система не може надійно відновити залежності, які в документації лише
маються на увазі. Такі місця залишаються роз'єднаними або позначаються як
низькодостовірні гіпотези й потрапляють у warnings. Це свідоме обмеження:
результат має бути перевірюваним, а ступінь упевненості — видимим, замість
переконливої вигадки.

Файл `examples/access_recovery_process.md` залишається окремою розміченою
фікстурою для перевірки математичного агрегатора зі статті. Web-застосунок його
не читає і не використовує як готову топологію. Фікстуру можна відтворити з
командного рядка:

```bash
process-hierarchy examples/access_recovery_process.md --pretty
```

### Перегляд PostgreSQL у DataGrip

Параметри локального підключення:

```text
Host: 127.0.0.1
Port: значення POSTGRES_PORT (типово 5432)
Database: значення POSTGRES_DB (типово segmenter)
User: значення POSTGRES_USER (типово segmenter)
Password: значення POSTGRES_PASSWORD
```

Порт опубліковано лише на loopback-інтерфейсі, тому PostgreSQL не відкривається
для зовнішньої мережі.

## Що робить

- обробляє plain text / markdown;
- виділяє headings, paragraphs, list items і окремі рядки Markdown-таблиць;
- розпізнає user stories;
- розпізнає acceptance criteria;
- розпізнає API operations;
- виконує sentence segmentation з винятками для `e.g.`, `i.e.`, `etc.`, API paths, versions;
- виконує `hard_process_split` для `and then`, `then`, `after that`, `next`;
- виконує `soft_process_split` для `if`, `when`, `unless`;
- повертає список `Fragment`.

## Встановлення

```bash
python -m venv .venv
source .venv/bin/activate  # Windows: .venv\Scripts\activate
pip install -e .
```

Для тестів:

```bash
pip install -e ".[dev]"
pytest
```

## Запуск прикладу

```bash
python -m fragment_segmenter.cli examples/checkout.md --artifact-id checkout_doc --format markdown
```

Або після встановлення entrypoint:

```bash
fragment-segment examples/checkout.md --artifact-id checkout_doc --format markdown
```

## Optional Unstructured adapter

У MVP основний шлях — rule-based parser, бо він краще зберігає line/char source positions.

Адаптер `UnstructuredPartitioner` залишено як optional extension:

pip install -e ".[unstructured]"

## Реалістичний корпус документації

Репозиторій містить два нерозмічені англомовні корпуси:

- `examples/access_recovery_source_docs/` — п'ять документів про відновлення
  доступу до корпоративного продукту;
- `examples/home_internet_connection_docs/` — вісім документів про перевірку
  адреси, укладання договору, планування виїзду, фізичний монтаж, активацію,
  приймання послуги та початок білінгу домашнього інтернету.

У цих файлах немає ідентифікаторів вершин і ребер, таблиць переходів або
готових кандидатів на агрегацію. Кожен каталог має лише декларативний
`example.json` із назвою, описом і переліком Markdown-файлів. Обидва корпуси
проходять той самий pipeline, що й завантажений ZIP; спеціального builder-а або
готової топології для них немає.

Наприклад:

```bash
fragment-segment \
  examples/home_internet_connection_docs/home_internet_order_fulfilment_guide.md \
  --pretty
```
